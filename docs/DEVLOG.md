## 2026-10-21 — Day 3: Analytics queries (plus the missed Day 2)

**Catch-up note:** Day 2 (20 Oct) was not pushed, so I finished it first. Slug validation now enforces 3-32 characters of `A-Za-z0-9_-`, lowercases slugs (so `Demo` and `demo` are the same link), and rejects reserved words like `api` and `up`. The short URL `GET /{slug}` now returns a 302 and logs the click (IP, user agent, referrer) in a transaction. The old `/api/links/{slug}` still works. The destination must now be `http` or `https`, so `javascript:` URLs are rejected.

**Built today (Day 3):** `GET /api/links/{slug}/analytics` and `GET /api/analytics` return total clicks, unique visitors (distinct IP), a zero-filled time series by day or ISO week, top referrer hosts ("Direct" when there is no Referer), and for the overview the top links. Query params: `days` (1-365) and `interval` (`day`|`week`). The queries live in `app/Services/ClickAnalytics.php`. 18 tests pass, and I smoke-tested it with curl against the running server.

**Concept — aggregation in SQL, shaping in PHP:** Asking the database to `GROUP BY date(created_at)` and `COUNT(*)` returns a few dozen small rows, even if the table has millions of clicks. Loading every click into PHP and counting there would be slow and memory-hungry. So the database counts, and PHP only does the final tidying. That tidying includes *zero-filling*: days with no clicks have no rows in the table, so a chart would skip them and draw a misleading line. We build every day in the range first, then add the counts into it. Weekly grouping is done by folding the daily counts into the Monday of each week, which works the same on SQLite, MySQL and Postgres. "Unique visitors" is `COUNT(DISTINCT ip)`, an approximation, because many people share one IP and one person can change IPs.

**Self-check:** A link got clicks on Monday and Thursday only. Why would a chart built straight from `GROUP BY date` mislead, and what does `timeSeries()` do to fix it? Bonus: why is `COUNT(DISTINCT ip)` only an approximation of real visitors?

## 2026-10-22 — Day 4: Link expiry and QR codes

**Built:** Links can now expire. `POST /api/links` accepts an optional `expires_at` (must be a valid future date); a new migration adds the nullable `expires_at` column. After that moment `GET /{slug}` (and `/api/links/{slug}`) return `410 Gone` and the visit is *not* logged as a click. New endpoint `GET /api/links/{slug}/qr` returns an SVG QR code that points at the short URL. Custom slugs were already done on Day 2, so they are untouched. Because Packagist was not reachable from the build machine, I wrote a small QR encoder myself (`app/Services/QrCode.php`, byte mode, error correction M, up to 213 characters) and checked its output with OpenCV's QR decoder on several strings. 27 tests pass (9 new), and I smoke-tested with curl. Tip: once network access to Packagist works, `bacon/bacon-qr-code` is the usual library choice.

**Concept — 410 vs 404, and how a QR code is made:** `404 Not Found` says "no idea what this is"; `410 Gone` says "this existed on purpose and was removed", which tells browsers and search engines to stop asking. Expiry is also checked at read time (`expires_at` is in the past?), not by a background job deleting rows, so it is exact to the second and the click history stays intact for analytics. A QR code is just your text turned into bytes, plus Reed-Solomon error-correction bytes (extra maths bytes so a scratched code still scans), laid out as black/white squares around three corner "finder" squares. Then 8 possible "masks" (checkerboard-like flips) are tried and the one with the fewest ugly patterns wins, so scanners don't get confused by big blank areas.

**Self-check:** Why do we compute "is it expired?" when the link is visited instead of deleting expired rows with a scheduled job? And what is the one thing that must NOT happen when an expired link is visited (hint: analytics)?

## 2026-10-23 — Day 5: React dashboard with click charts

**Built:** The Vite starter page is replaced by a real dashboard. You can create a short link (with optional custom slug and expiry) and see server validation errors inline. Click a link to see its QR code and its own analytics; click it again to go back to "all links". A range picker (7/30/90 days) and a day/week toggle drive the data. It shows total clicks, unique visitors, an SVG line chart of clicks over time with hover tooltips, and bar lists for top referrers and top links. The charts are hand-written SVG, with no chart library. Files: `frontend/src/api.js`, `chartMath.js`, `components/*`. I tested it against the running Laravel API in a headless browser (create link, QR, filters, no console errors). The backend's 27 tests still pass. Screenshot: `docs/dashboard.png`.

**Concept — mapping data to pixels, and "stale" responses:** A chart is just a function from numbers to coordinates. In SVG the y axis points down, so a bigger value means a smaller y: `y = height - (value / max) * height`. We round the max up to a tidy number (`niceMax`) so the axis ends on 5, 30 or 200 and not on 23. Because the API already zero-fills missing days, the line has no misleading gaps. On the React side, each time you change a filter we fetch again inside `useEffect`. If you click quickly, a slow old response could arrive after a newer one and overwrite it. The `stale` flag in the effect's cleanup function stops that: the old effect marks itself stale, and its result is ignored.

**Self-check:** Why does `toPoints` compute `height - (clicks / max) * height` instead of just `(clicks / max) * height`? And what bug would appear without the `stale` flag if you switch from "7 days" to "90 days" on a slow network?

**Concept — what makes a test useful:** A test is a small program that states what must stay true, so you can change code later without fear. Good tests target *boundaries* (exactly 3 and 32 characters, a click at exactly the start second, a link expiring between two requests) because that is where off-by-one bugs live. `travelTo()` freezes or moves the clock so time-based features are repeatable. Unit tests call one class directly and are fast; feature tests send a real HTTP request through routes, validation and the database, so they prove the pieces fit together. On the frontend, Testing Library tests what a user sees (labels, buttons, alerts), not internal state, so refactoring a component does not break its tests. Two gotchas I hit: PHPUnit 12 needs `#[DataProvider]` attributes instead of `@dataProvider` comments, and in vitest a `beforeEach(() => mock.reset())` arrow function *returns* the mock, which vitest treats as a cleanup function and calls after the test, so always write `beforeEach(() => { ... })` with braces.

## 2026-10-25 — Day 7: Security pass

**Built:** A review of validation, abuse limits, secrets and dependencies. (1) New `SafeDestination` validation rule: no spaces/control characters, no `https://bank.com@evil.com`-style credentials, no links back to the shortener itself (redirect loops), no `localhost`, private ranges or the cloud-metadata address `169.254.169.254`. (2) Rate limiting with three named limiters per IP: 10 creates/min, 120 API reads/min, 300 redirects/min, returning 429 with `Retry-After`. (3) A `SecurityHeaders` middleware (nosniff, frame deny, referrer and permissions policy, plus a strict CSP on the SVG QR). (4) `TRUSTED_PROXIES` support so the real visitor IP is used behind a load balancer. (5) `npm audit fix` cleared 2 high issues in vite/source-map-js (now 0). `composer audit` could not run here because Packagist is blocked from this sandbox, so please run it locally. A secrets scan found nothing and `.env` is git-ignored. 29 new tests; backend is now 99 tests, all passing, and a live curl smoke test matched. Honest finding: with `APP_DEBUG=true` (the `.env.example` default) error JSON includes a full stack trace with file paths, so production must set it to false; there is now a comment saying so. Known gap: there is still no authentication.

**Concept — never trust input, and limit how fast it arrives:** Anything a user sends is hostile until validated. A URL shortener is a redirect machine, so the dangers are where it can send people: phishing tricks (`user@host`), internal addresses (SSRF-style targets like `localhost` or the metadata IP, which matter the moment any server ever fetches a link), and loops back to itself. Validate on the server with an allow-list mindset (what is permitted) rather than trying to list everything bad. Rate limiting counts requests per key (here the IP) in a cache over a time window and answers 429 once the count is exceeded; it protects the database, hides nothing, and is only as good as the IP you see, which is why proxies need `TRUSTED_PROXIES`. Headers like `nosniff` tell the browser not to guess a file's type, so an SVG can't be treated as a script. Dependency audits matter because most of your code is other people's.

**Self-check:** Why is `https://mybank.com@evil.example/` dangerous, and which part of the URL does the browser actually visit? Also: why is a per-IP rate limit weaker when many users share one office IP, and what does `TRUSTED_PROXIES` change?

## 2026-10-26 — Day 8: Dockerfile and GitHub Actions CI

**Built:** (1) A multi-stage `Dockerfile`: stage one builds the React dashboard with Vite (`--base=/dashboard/`), stage two runs `composer install --no-dev`, stage three is a small `php:8.3-cli-alpine` image that copies in only the results, runs as `www-data`, sets production env vars, keeps the SQLite file in a `/data` volume and has a `HEALTHCHECK` on `/up`. `docker/entrypoint.sh` creates a temporary `APP_KEY` if none is given, runs migrations and starts the server. (2) `docker-compose.yml` for one-command local runs, and a `.dockerignore`. (3) `.github/workflows/ci.yml` with three jobs: backend (PHP 8.3, `php artisan test`, `composer audit`, advisory `pint --test`), frontend (`npm ci`, lint, vitest, build, `npm audit`) and docker (build the image, start it, curl `/up`, the dashboard, create a link and check the 302). (4) Fixed the old `routes/web.php` import-order style issue. The frontend steps and the `--base=/dashboard/` build were run locally (lint clean, 26 tests, build OK). Honest caveat: this sandbox has no Docker daemon and cannot reach Packagist, so the Dockerfile, the PHP CI steps and the container smoke test have NOT been run here. Their first real run is the GitHub Actions run on this push; please check the Actions tab and, locally, run `docker compose up --build`. If something fails, paste the log and we fix it on Day 9.

**Concept — images, layers and CI:** A Docker image is a stack of read-only layers, one per Dockerfile instruction. Docker caches a layer until its input changes, so we copy `composer.json`/`package.json` and install dependencies *before* copying the source: editing code does not re-download every package. Multi-stage builds use heavy tools (Node, Composer) to produce files, then leave them behind; the final image has only PHP and the app, so it is smaller and has less to attack. Running as a non-root user means a compromised app cannot do root things inside the container. A volume keeps data (the SQLite file) outside the container, which can be thrown away and replaced at any time. CI (continuous integration) is a robot that runs your checks on a clean machine for every push, so "works on my laptop" has to become "works from scratch". A smoke test starts the real thing and makes one realistic request to prove the pieces are wired together.
